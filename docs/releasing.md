# 维护者发布流程

1. 在 `VERSION` 中确定新版本；更新 `CHANGELOG.md` 和 `docs/releases/v版本.md`，写清范围与尚未验收的内容。
2. 审阅四套技能文件后更新各自的 `toolkit-manifest.json`：同一版本号，包含该目录除清单本身外的公开文件 SHA-256。该清单用于安装完整性检查，不是秘密扫描器。
3. 审阅全部改动后更新 `PUBLIC_FILES.sha256`，运行测试与清单检查，提交到主分支并等待 CI 成功。
4. 对该提交建立 `v版本` 标签并推送。发布工作流核对标签、重新运行检查，并从审阅清单构建 ZIP 和 `SHA256SUMS`，再创建 GitHub Release。带 `-` 的版本标记为预发布。
5. 回读 Release 的标签、预发布状态、附件及下载包校验和，再交付链接。已发布标签与包不覆盖；修复使用新版本。

本地构建必须在干净提交中运行：

```bash
python3 scripts/build_release.py --output output/release
```

构建使用明确文件清单，不打包工作区的 `local/`、缓存、凭据或其他未审阅内容。包内附加生成的 `RELEASE.json` 记录源提交，包内清单同时包含该元数据的哈希。ZIP 使用固定文件顺序与时间戳。

工作流失败时检查失败阶段。若尚未生成 Release，可在修复条件后重跑；已存在 Release 时不会自动覆盖附件。用户体验与真实平台验收应单独记录，不能由脚本检查结果替代。
